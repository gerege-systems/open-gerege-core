# Migration-ий дугаарлалтын конвенц

Энэ хавтас доторх `N_нэр.up.sql` / `N_нэр.down.sql` файлууд Postgres схемийг
хөгжүүлдэг. Runner (`internal/datasources/migration`) нь:

- файлуудыг **`N` дугаараар тоон эрэмбэлж** ажиллуулна (лексикограф биш);
- хэрэгжсэн эсэхийг `schema_migrations` хүснэгтэд **файлын нэрээр** тэмдэглэнэ.

Эндээс хоёр чухал зүйл гарна:

1. **Файлын нэрийг өөрчилвөл** тэр migration хэрэгжээгүйд тооцогдож
   production дээр **дахин ажиллана**. Тиймээс хэрэгжсэн migration-ий нэрийг
   хэзээ ч дур мэдэн бүү сольж болохгүй — `schema_migrations`-ыг зэрэг
   шинэчлэх SQL-тэй хамт, засварын цонхонд л хийнэ.
2. **Дугаар нь зөвхөн эрэмбэ** тодорхойлно. Хоёр өөр repo нэг дугаарыг
   өөр өөр зорилгоор ашиглавал merge хийхэд эрэмбэ будлиантана.

## Дугаарын мужууд

| Муж | Эзэн | Тайлбар |
|---|---|---|
| `1 – 999` | **Суурь (core)** | `template-dgov-mn` / `template-gerege-mn` дээр үүсдэг, бүх апп руу дамждаг |
| `1000 – ∞` | **Апп өөрийн** | Ring, Хурдан, Developer, SSO, Wallet г.м. зөвхөн тухайн платформд хамаарах |

Энэ репогийн муж нь [`RANGE`](RANGE) файлд бичигдсэн (эхлэл ба төгсгөл, зайгаар).

## Дүрэм

- Шинэ migration нэмэхдээ **өөрийн мужаас** дараагийн сул дугаарыг ав.
- Нэг дугаарыг хоёр файлд бүү өг — эрэмбэ файлын нэрээр санамсаргүй шийдэгдэнэ.
- `.up.sql` бүрд `.down.sql` хостой байх ёстой.
- Эдгээрийг `migration_range_test.go` автоматаар шалгана — зөрчвөл CI унана.

## `LEGACY` файл

Конвенц тогтоохоос өмнө үүссэн, production-д аль хэдийн хэрэгжсэн
migration-ууд [`LEGACY`](LEGACY)-д жагсаагдсан. Тэдгээр нь мужийн болон
давхардлын шалгалтаас чөлөөлөгдөнө — нэрийг нь өөрчлөх нь production DB-д
эрсдэлтэй тул байгаагаар нь үлдээв. **Энэ жагсаалтад шинэ мөр бүү нэм.**

Хожим засварын цонхонд цэгцлэх бол `scripts/renumber-migrations.py`-г
ашиглана — файлыг дахин дугаарлаад `schema_migrations`-д тавих
`UPDATE`-үүдийг хамт үүсгэнэ.
