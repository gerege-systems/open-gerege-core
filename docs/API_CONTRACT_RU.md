# Контракт API

> 🌐 **Русский** · [English](API_CONTRACT.md) · [Монгол](API_CONTRACT_MN.md) · [中文](API_CONTRACT_ZH.md)

Справочник REST API для **Gerege Template Platform V3.0**
(Цахим үйлчилгээг бүтээх суурь) — готовой к продакшену основы для создания
цифровых услуг (Go-бэкенд на Clean Architecture + Next.js BFF + Gemini AI).
Контракт отражает эталонное развёртывание **Gerege Template Platform**
(template.gerege.mn) — платформу государственных и частных услуг на базе eID.
Живая автогенерируемая спецификация доступна по `GET /swagger/`
(источник: `docs/swagger.json`).

> **О путях.** Каждый модуль ниже монтируется в группе `/api`, а каждая группа
> маршрутов добавляет префикс `/v1`, поэтому реальный путь запроса —
> `/api/v1/<group>/…`, хотя аннотации swagger `@Router` написаны относительно
> (например, аннотация `/auth/eid/start` → реальный путь
> `/api/v1/auth/eid/start`). В таблицах этого документа указаны **полные** пути.

## Соглашения

- **Базовый URL:** `http://localhost:8080/api/v1`
- **Content-Type:** `application/json`
- **Аутентификация:** защищённые endpoint требуют
  `Authorization: Bearer <access_token>` (токены выдаются потоками входа eID / Google ниже)
- **Лимиты (на IP):** `/auth/*` ~5 запросов/мин, `/auth/eid/poll` отдельный более
  мягкий лимит ~60 запросов/мин (длинный опрос не должен сам себя ронять в 429),
  `/ai/*` ~20 запросов/мин, а **изменяющие** endpoint `/gov`, `/gspace`, `/me`,
  `/users/me/eid` — ~30 запросов/мин (при превышении 429)
- **Ограничение тела:** тела `/auth/*` и `/provider/*` ограничены 4 КиБ; остальные — 1 МиБ

### Конверт ответа

Каждый ответ использует единый конверт:

```json
{
  "status": true,
  "message": "human-readable summary",
  "data": { },
  "request_id": "b1d2…"
}
```

- `status` — `true` при успехе, `false` при ошибке
- `data` — присутствует при успехе (отсутствует/null при ошибке)
- `request_id` — идентификатор корреляции (дублируется в заголовке `X-Request-ID`)

### Коды состояния

| Код | Значение | Когда |
|------|---------|------|
| 200 | OK | Успешное чтение / действие |
| 201 | Created | Ресурс создан |
| 400 | Bad Request | Некорректное тело |
| 401 | Unauthorized | Токен отсутствует/неверен/истёк |
| 403 | Forbidden | Аутентифицирован, но нет нужной роли/разрешения |
| 404 | Not Found | Ресурс не существует |
| 409 | Conflict | Дубликат / конфликт состояния |
| 422 | Unprocessable Entity | Ошибка валидации (см. ниже) |
| 429 | Too Many Requests | Превышен лимит запросов |
| 500 | Internal Server Error | Непредвиденный сбой (причина в логах, клиенту общее сообщение) |

### Ошибка валидации (422)

Детали по полям возвращаются в `data.errors` — это **массив** объектов
`{ field, tag, message }`. `field` — это имя из JSON-тега:

```json
{
  "status": false,
  "message": "validation failed",
  "data": { "errors": [ { "field": "target_lang", "tag": "required", "message": "target_lang is required" } ] },
  "request_id": "b1d2…"
}
```

### Обозначения

- 🔒 — требуется `Authorization: Bearer <access_token>`
- 🛡️ `perm` — дополнительно требуется указанное разрешение RBAC (роль **админа**
  автоматически получает полный каталог разрешений; там, где отмечено, нужен
  **суперадмин**). Параметры пути показаны в `{фигурных скобках}`.

## Аутентификация (`/api/v1/auth`)

**Единственный** способ входа — **вход через eID** (доверяющая сторона eID
Mongolia) плюс привязка аккаунта **Google OAuth**. Нет ни паролей, ни email/OTP,
ни регистрации. Для этой группы действуют лимит запросов и ограничение тела
(4 КиБ); потоки до входа выполняются под сервисной личностью RLS.

| Метод | Путь | Аутентификация | Описание |
|--------|------|------|-------------|
| POST | `/auth/eid/start` | — | Начать вход через eID; возвращает QR-код / мобильный deep-link и токен сессии для опроса. |
| POST | `/auth/eid/start-id` | — | Начать вход по регистрационному номеру; отправляет подтверждение на зарегистрированное устройство гражданина. |
| POST | `/auth/eid/poll` | — | Длинный опрос ожидающей сессии eID (удержание ~25 с); возвращает `PENDING` либо, после подтверждения, пару access + refresh. Отдельный более мягкий лимитер. |
| POST | `/auth/google` | — | Колбэк Google OAuth — обменивает `code`, затем привязывает аккаунт Google к пользователю eID (или входит под ним). |
| DELETE | `/auth/google/link` | 🔒 | Отвязать аккаунт Google у аутентифицированного пользователя (привязка возможна только через поток входа). |
| POST | `/auth/refresh` | — | Ротация пары токенов по действующему refresh-токену. Refresh **ротирует** токен, поэтому старый становится недействительным. |
| POST | `/auth/logout` | — | Отозвать переданный refresh-токен; если передан и `access_token`, его `jti` попадает в список запрещённых Redis и он немедленно перестаёт работать. |

При успехе потоки входа/обновления возвращают пару токенов в `data`
(`token` — access JWT, `refresh_token` — refresh JWT) вместе с данными
пользователя (`id`, `role_id`, поля имени).

## API-шлюз (`/api/v1/gateway`) 🛡️ `gateway.manage`

Реестр upstream-**сервисов** и телеметрия. Каждый endpoint требует 🔒 + 🛡️
`gateway.manage`. **Клиенты** шлюза (прежние «consumers + API-ключи») теперь
находятся в группе **Applications** ниже; каждый сервис несёт `scope`
(OAuth-scope, который приложения запрашивают для доступа к нему). Прежние
маршруты и политики в стиле Kong удалены (их не использовал ни один рантайм-прокси).
**Журнал запросов** теперь настоящий: middleware записывает каждый реальный
запрос к `/api` (метод/путь/статус/задержка/client_ip) — обзор агрегируется из него.

| Метод | Путь | Описание |
|--------|------|-------------|
| GET | `/gateway/overview` | Обзор телеметрии (число сервисов/приложений + статистика запросов за 24 ч по реальному трафику). |
| GET | `/gateway/logs` | Реальный журнал запросов (метод/путь/статус/задержка/client_ip). |
| GET | `/gateway/services` | Список сервисов. |
| POST | `/gateway/services` | Создать сервис (его OAuth-`scope` = `svc:`+имя). |
| PUT | `/gateway/services/{id}` | Обновить сервис. |
| DELETE | `/gateway/services/{id}` | Удалить сервис. |

## Applications (`/api/v1/applications`) 🛡️ `gateway.manage`

Единый **реестр OAuth2-клиентов** — объединённая замена прежних «consumers +
API-ключи» шлюза и отдельной регистрации RP в SSO. Каждое приложение — это
**OAuth2-клиент Ory Hydra**; его доступ к сервисам выражается OAuth-**scope**
(`application_services` → `gateway_services.scope`). Каждый endpoint требует
🔒 + 🛡️ `gateway.manage`, а сама группа **регистрируется только при настроенной
Hydra** (`ProviderConfigured()`).

`app_type` выбирает grant и способ аутентификации:

| `app_type` | Grant | Клиент | Использование |
|------------|-------|--------|-----|
| `web` | `authorization_code` (+ `refresh_token`) | конфиденциальный (secret) | RP «Login with DAN» — серверное веб-приложение |
| `spa` | `authorization_code` (+ `refresh_token`) | **публичный** (PKCE, без secret) | SPA в браузере |
| `native` | `authorization_code` (+ `refresh_token`) | **публичный** (PKCE, без secret) | Мобильное / нативное приложение |
| `m2m` | `client_credentials` | конфиденциальный (secret) | Сервер-сервер |

**`client_secret`** OAuth2 (только для конфиденциальных типов) показывается
**один раз** — в ответе на создание / ротацию — и больше никогда.

| Метод | Путь | Описание |
|--------|------|-------------|
| GET | `/applications` | Список приложений. |
| POST | `/applications` | Создать; создаёт OAuth2-клиента Hydra и возвращает приложение вместе с одноразовым `secret` (для конфиденциальных типов). |
| GET | `/applications/{id}` | Получить одно приложение. |
| PUT | `/applications/{id}` | Обновить наложение и желаемое состояние клиента Hydra. |
| DELETE | `/applications/{id}` | Удалить клиента Hydra и наложение. |
| POST | `/applications/{id}/rotate-secret` | Выдать новый секрет клиента, возвращается один раз (только конфиденциальные). |
| PUT | `/applications/{id}/services` | Заменить разрешённые сервисы шлюза — они становятся OAuth-scope клиента. |

**Тело создания/обновления** — `{ name, app_type (web\|spa\|native\|m2m), redirect_uris[], tags[], service_ids[], enabled }`;
**тело установки сервисов** — `{ service_ids[] }`.

## Провайдер OIDC — вход/согласие/выход (`/api/v1/provider`)

Активен **только при настроенном провайдере** (`ProviderConfigured()`). Это
платформа в роли **провайдера** OIDC (её собственный встроенный Go-провайдер);
страницы `/login`, `/consent`, `/logout` в Next.js BFF обращаются сюда.
Тело ограничено 4 КиБ. Endpoint `get`/`reject`/`logout-accept`
аутентифицируются по challenge (без bearer); endpoint `accept` требуют вошедшего
гражданина (subject = ID пользователя dan).

| Метод | Путь | Аутентификация | Описание |
|--------|------|------|-------------|
| GET | `/provider/login` | challenge | Получить детали login-challenge. |
| GET | `/provider/consent` | challenge | Получить детали consent-challenge. |
| POST | `/provider/login/reject` | challenge | Отклонить login-challenge. |
| POST | `/provider/consent/reject` | challenge | Отклонить consent-challenge. |
| POST | `/provider/logout/accept` | challenge | Принять logout-challenge. |
| POST | `/provider/login/accept` | 🔒 | Принять login-challenge для вошедшего гражданина. |
| POST | `/provider/consent/accept` | 🔒 | Принять consent-challenge. |

## Суперадмин (`/api/v1/superadmin`) 🔒

Закрыт `RequireSuperAdmin` — доступ есть только у `RoleSuperAdmin`; обычный

## AI (конвейер Gemini) (`/api/v1/ai`) 🔒

Все endpoint `/ai/*` требуют bearer-токен и делят отдельный лимит запросов
(~20 запросов/мин на IP). Пока не настроен `GEMINI_API_KEY`, они возвращают 500.
Ассистент работает на слоистом системном промпте — жёстко заданные ограничения +
настраиваемая админом **область применения** (всё вне неё отклоняется) +
необязательные **инструкции** — и опирает ответы о платформе на таблицу
`ai_knowledge` через инструмент `search_knowledge`.

### POST `/ai/chat` 🔒

Чат с ассистентом. Отправляйте текст, голос (аудио в base64, которое модель
понимает напрямую) или и то и другое. Без состояния — предыдущие реплики
передавайте в `history`.

**Запрос**

```json
{ "message": "what time is it?",
  "audio": { "mime": "audio/webm", "data": "<base64>" },
  "history": [ { "role": "user", "text": "…" }, { "role": "model", "text": "…" } ] }
```

| Поле | Правила |
|-------|-------|
| `message` | необязательно (обязательно, если нет `audio`), ≤ 4000 символов |
| `audio` | необязательно; `mime` ∈ webm/ogg/wav/mpeg/mp3/mp4/m4a/aac/flac, `data` base64 ≤ ~700 КБ |
| `history` | необязательно, ≤ 20 реплик |
| `lang` | необязательный язык интерфейса — `mn` \| `en` \| `zh` \| `ru`; ассистент отвечает на нём (пусто ⇒ `mn`) |

**Ответ `200`**

```json
{ "status": true, "message": "ai reply generated", "data": {
  "reply": "Одоо 12:30 цаг болж байна.",
  "steps": [ { "tool": "get_server_time", "args": {}, "result": { } } ],
  "degraded": false }, "request_id": "…" }
```

`steps` перечисляет вызовы функций, выполненные моделью (трассировка конвейера).
Когда Gemini временно недоступен, endpoint всё равно возвращает `200` с резервным
`reply` на языке пользователя и `degraded: true`.

### POST `/ai/stt` 🔒

Речь в текст. **Запрос** `{ "audio": { "mime": "audio/webm", "data": "<base64>" } }`
**Ответ `200`** — `data: { "text": "…" }` (пусто, если речь не обнаружена).

### POST `/ai/tts` 🔒

Текст в речь. **Запрос** `{ "text": "Сайн байна уу", "voice": "Kore" }`
(`voice` необязателен) **Ответ `200`** —
`data: { "mime": "audio/wav", "data": "<base64 WAV>" }` — воспроизводится в браузере напрямую.

### POST `/ai/translate` 🔒

Синхронный перевод. Передайте `text` **или** `audio` (аудио сначала проходит
внутренний шаг STT); `speak: true` дополнительно вернёт озвученную версию.
Тихие фрагменты возвращают пустые поля — интерфейс синхронного перевода шлёт сюда
короткие записанные фрагменты.

**Запрос** `{ "audio": { … }, "target_lang": "en", "speak": false }`
(`target_lang`: обязателен, например `mn|en|ru|zh|ja|ko|de`)
**Ответ `200`** — `data: { "source_text": "Сайн уу", "translated": "Hello", "audio": { … } }`.

### POST `/public/ai/chat` 🌐
**Без аутентификации.** Обслуживает плавающий чат-виджет на главной странице —
посетитель может спросить о платформе до входа в систему. Тот же конвейер, что и
у `/ai/chat`, но с более жёсткими ограничениями для открытой поверхности:

| Ограничение | Значение |
|-------------|----------|
| Rate limit | ~6 запросов/мин на IP (burst 3) — отдельно от лимитера `/ai/*` |
| `message` | обязательно, ≤ 1000 символов |
| `history` | опционально, ≤ 6 реплик, каждая ≤ 1000 символов |
| `lang` | опционально — `mn` \| `en` \| `zh` \| `ru` |
| `audio` | необязательный фрагмент push-to-talk — тот же белый список mime, что и у `/ai/chat`, но `data` base64 ≤ ~250 КБ (≈ 15 с opus). Требуется либо `message`, либо `audio` |
| Инструменты | только поиск по базе знаний — usecase собран с урезанным набором инструментов, поэтому до инструментов с пользовательскими данными не добраться |
| Промпт | дополнительный жёстко зашитый слой: никогда не спрашивать личные данные и не заявлять о доступе к аккаунту |

**Ответ `200`** — та же структура, что и у `/ai/chat` (`reply`, `steps`, `degraded`).

### POST `/public/ai/tts` 🌐
**Без аутентификации.** Кнопка «прослушать» в виджете на главной — озвучивает
один ответ помощника. Использует общий лимитер `/public/ai/*` (~6 запросов/мин
на IP), `text` ≤ 800 символов, голос выбирается на сервере (вызывающая сторона
не может указать модель или голос).

**Запрос** `{ "text": "…" }` · **Ответ `200`** — `data: { "mime": "audio/wav", "data": "<base64 WAV>" }`

> Настройка слоёв промпта описана выше в разделе **Админ — пользователи и промпты
> AI** (`GET`/`PUT /api/v1/admin/ai/prompts`). Базовый слой ограничений жёстко
> задан и никогда не раскрывается.

## Монтирования вне `/api`

### Административная поверхность провайдера OIDC — `/admin` (оператор)

Активна **только при настроенной Hydra** (`ProviderConfigured()`). Это обычный
`http.ServeMux`, смонтированный на `/admin` (через `StripPrefix`, поэтому его
внутренние шаблоны читаются как `/api/v1/…`). Она управляет **регистрацией
OAuth2-клиентов RP** и **админскими API-ключами** и аутентифицируется
**админским API-ключом** — `Authorization: Bearer <key>` или `X-API-Key: <key>` —
а **не** пользовательским JWT.

> ⚠️ **Совпадение названий.** Эта поверхность `/admin` верхнего уровня — не то же
> самое, что внутренняя группа `/api/v1/admin` выше. Её собственные маршруты после
> strip тоже выглядят как `/api/v1/…`, но доступны по `/admin/api/v1/…`.

| Метод | Путь (внутри `/admin`) | Описание |
|--------|-----------------------|-------------|
| GET | `/api/v1/me` | Определить вызывающий админский ключ. |
| GET | `/api/v1/clients` | Список зарегистрированных OAuth2-клиентов RP. |
| POST | `/api/v1/clients` | Зарегистрировать нового клиента RP. |
| GET | `/api/v1/clients/{client_id}` | Получить одного клиента RP. |
| PATCH | `/api/v1/clients/{client_id}` | Обновить клиента RP. |
| DELETE | `/api/v1/clients/{client_id}` | Удалить клиента RP. |
| POST | `/api/v1/clients/{client_id}/rotate-secret` | Сменить секрет клиента RP. |
| GET | `/api/v1/keys` | Список админских API-ключей. |
| POST | `/api/v1/keys` | Создать админский API-ключ. |
| DELETE | `/api/v1/keys/{id}` | Отозвать админский API-ключ. |

### Ретранслятор подписи — `/rp/sign/*` (прокси RP)

Активен **только когда заданы и `SIGN_RELAY_TOKEN`, и `EID_RP_SECRET`**.
Это обратный прокси, позволяющий сторонним RP подписывать через учётные данные
dan в eID Mongolia: вызывающий передаёт общий токен ретранслятора как
`Authorization: Bearer <token>`; ретранслятор заменяет его на настоящий секрет RP
dan и пересылает запрос в eID Mongolia. Обрабатываются и `/rp/sign`, и `/rp/sign/*`.
