# Migration бодлого ба модулийн migration engine

> V4.0 Modular Platform · Phase 2. Хэрэгжилт: `kernel/data/migrate`.
> Модуль хөгжүүлэх ерөнхий гарын авлага: [MODULES.md](MODULES.md).

## Хоёр engine зэрэг оршино (санаатай)

| | Глобал (хуучин) | Модулийн (шинэ) |
|---|---|---|
| Код | `core/datasources/migration` | `kernel/data/migrate` |
| Файлууд | `migrations/N_name.up.sql` | `modules/<id>/migrations/N_name.up.sql` |
| Төлөв | `schema_migrations` | `mod_<id>_schema_migrations` |
| Дугаарлалт | репо даяар нэг муж (`RANGE`) | модуль дотроо 1-ээс |

Шилжилт нь **модуль тус бүрээр** явна. Өөрийн `Migrations()` зарлаагүй
модуль глобал engine дээрээ хэвээр ажиллана — өөрчлөлт шаардлагагүй.
Тиймээс энэ нь нэмэлт (additive) бөгөөд аль ч үед зогсоож болно.

## Шинэ модульд migration нэмэх

```go
//go:embed migrations/*.sql
var migrationsFS embed.FS

func (*Module) Migrations() migrate.MigrationFS { return migrationsFS }
```

Файлын нэр: `1_baseline.up.sql`, `2_add_index.up.sql` … (модуль дотроо
1-ээс, тоон эрэмбэ — лексикограф БИШ).

## Adopt: ажиллаж буй DB-г хэрхэн таних вэ

`ShouldAdopt` нь DB-д схем аль хэдийн боссон эсэхийг **хоёр дохиогоор**
шалгана:

1. глобал `schema_migrations` хүснэгт байгаа БА мөртэй, **эсвэл**
2. sentinel хүснэгт (`users`) байгаа.

Үнэн бол модулийн baseline-ууд **ажиллахгүй**, зөвхөн "хэрэгжсэн" гэж
бүртгэгдэнэ (`AdoptAll`).

**Яагаад зөвхөн (1) хангалтгүй вэ.** Схем нь бүрэн боссон атлаа бүртгэл нь
хоосон DB бодитоор оршдог: `pg_dump`/`restore` нь бүртгэлийн мөрийг
авчрахгүй байж болно, мөн integration harness нь `.up.sql`-уудыг
runner-ээр биш шууд ажиллуулдаг. Зөвхөн бүртгэл дээр шийдвэл эдгээр DB
"шинэ" гэж андуурагдаж, runner нь **амьд хүснэгт дээр `CREATE TABLE`**
ажиллуулна. Энэ эрсдэлийг `TestAdoptDetectsSchemaWithoutBookkeeping`
барьдаг.

Шийдвэр нь модуль бүрт биш, **DB-д нэг удаа** тавигдана — хагас шилжсэн
төлөв үүсгэхгүй.

## Migration бодлого: expand–contract

Одооноос **эвдрэлтэй схемийн өөрчлөлтийг хоёр release-д хуваана**:

1. **Expand** — нэмэх л (nullable багана, шинэ хүснэгт, шинэ индекс).
   Хуучин болон шинэ код хоёулаа ажиллана.
2. **Contract** — хуучин код бүрэн гарсны дараа хуучин баганыг хасна.

**Rollback нь down migration-аас БИШ, өмнөх binary-г буцаахаас хамаарна.**
Expand алхам нь хуучин кодтой нийцтэй тул binary-г буцаахад схем засах
шаардлагагүй.

`Down` нь engine-д байгаа боловч **зөвхөн хөгжүүлэлт/тестэд**. Production-д
хэзээ ч найдаж болохгүй: өгөгдөл алддаг, зэрэгцээ ажиллаж буй сүүлийн
хувилбартай зөрчилддөг.

Практик дүрмүүд:

- `NOT NULL` баганыг **default-гүйгээр** шууд бүү нэм — эхлээд nullable,
  дараа нь backfill, эцэст нь хязгаарлалт.
- Багана/хүснэгтийг **дахин бүү нэрлэ** — шинийг нэмж, хоёуланд нь бич,
  дараа нь хуучныг хас.
- Том хүснэгтэд индекс нэмэхдээ `CREATE INDEX CONCURRENTLY` (транзакцаас
  ГАДУУР — тусдаа migration файлд).
- Хасах migration бүрт "хамгийн эрт хэзээ" гэдгийг тайлбартаа бич.

## Модуль хоорондын гадаад түлхүүр

Модулийн migration-ууд **бүртгэлийн дарааллаар** ажиллана
(`platformModules()`). `org` нь `users`-ээс хамаардаг тул `users` эхэлж
бүртгэгддэг — тэр дараалал migration-д ч мөн хүчинтэй.

Шинэ модуль өөр модулийн хүснэгт рүү FK тавьж байвал манифестийн
`DependsOn`-д тэрхүү модулийг **заавал** бич; эс бөгөөс шинэ DB дээр
дараалал баталгаагүй болно.

## Юуг ЗОРИУД хийгээгүй вэ: `SET SCHEMA`

Плангийн ноорогт модуль бүрийг Postgres-ийн тусдаа schema руу
(`ALTER TABLE ... SET SCHEMA`) нүүлгэх санаа байсан. Хэрэгжүүлээгүй:

- Модуль хооронд **гадаад түлхүүр олон** (`users` ×6, `roles` ×4 г.м.).
- **11 файлд RLS policy** — schema хилээр дамжихад policy-уудыг дахин
  зохиох шаардлагатай.
- Go давхаргын гар бичмэл SQL нь **бүхэлдээ схемгүй (unqualified) нэр**
  ашигладаг ба кодод `search_path` удирдлага **огт байхгүй** — холболт
  бүр (RLS транзакц дотор ч) search_path тохируулах шаардлагатай болно.

Migration-ийн **төлөв**-ийг тусгаарлахад физик тусгаарлалт шаардлагагүй.
Хэрэв хожим хэрэгтэй бол тусдаа, болгоомжтой PR-аар — энэ engine түүнд
саад болохгүй.
